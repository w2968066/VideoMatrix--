# 随机首帧单次编码验证（v2.6.0）

## 实现边界

- 从本条实际选中的素材裁切区间独立定位提取一帧 PNG，不等待主解码走到随机时间点。
- 首帧在主混剪末端合成，正常路径每个视频仅一次视频编码；插入时原音画一起后移一帧，新增帧静音。
- 不追求封面与最终成片逐像素一致：不含软件新增字幕、水印及去重效果。正文处理不变。
- 已撤回“同盘工作目录 → 完成后 rename”的方案：用户三条真实输出全部遇到 WinError 32，证明该方案未解决问题。
- 现改为编码前 O_EXCL 独占预留唯一正式 MP4，直接编码到该文件；成功后无 rename/replace/copy。临时封面放系统临时目录，产出列表只登记成功文件。
- 失败/停止只清理本次独占的未完成文件，不覆盖或清理用户既有输出。完成后即使文件被读者占用也无提交操作需要重试。

## 首轮短片对比（不可外推为性能结论）

执行：`python -m tests.benchmark_fused_cover`（backend 目录）。测试仅使用自动生成的素材和临时目录。

同一 1920×1080 / 30fps / 8000k 合成素材；每条 6 秒、6 段；每批 2 条、2 路并发。各条件先预热一批，再交替测量 3 批。所有编码均为 `h264_nvenc`，没有降级；源文件哈希未变化。以下耗时为**一批两条全部完成**的中位数，不是单条耗时。

| 模式 | 旧流程 | 单次编码 | 批次耗时减少 | FFmpeg 合计工作集峰值：旧 → 新 |
|---|---:|---:|---:|---:|
| 替换首帧 | 3.580 秒 | 1.982 秒 | 44.6% | 869.3 → 810.6 MiB |
| 插入一帧 | 3.662 秒 | 2.225 秒 | 39.2% | 871.4 → 806.2 MiB |

旧流程每批 4 次视频编码，新流程每批 2 次。工作集每 50ms 采样，表中取三批最高值，仅包括已追踪的 FFmpeg/探测子进程，不是 GPU 显存或全应用内存。对比基线使用同一核心关闭融合首帧，再调用保留的旧后处理器；不能将以上合成短片结果保证为用户长素材的加速比例。

## 用户长片回归

用户三条输出耗时 12.4 / 84.2 / 74.5 秒，全部提交失败。日志明确使用 NVIDIA 编码，没有 CPU 降级；封面 PNG 在开工约 1 秒后已写完，主要耗时在后续编码。

使用 720×1280 / 30fps / 32.5–33.9 秒 Hook，加 2160×3840 / 59.94fps / 15.649 秒 Body 复现，输出 1350×2400 与 1116×1984、24fps，两路工作集峰值达到约 14GB，并发生 CUDA 重试；关闭首帧仍有明显高内存问题。短片基准不足以验收此路径；长片性能修复必须另行验证，不能继续承诺整体加速 39%–45%。

修正：原视频输入加 `-an`，末尾追加原素材 `-vn` 音频输入，复制同一输入 seek；原音频滤镜改用独立音频输入的索引。保留 combined concat 和后续配乐/字幕/水印顺序，不增加视频解码/转码。只减少滤镜线程、拆开 concat 或缩小输入 packet 队列均未解决内存问题。

两路同素材、同规格的原生 FFmpeg 对比：原输入共享方案 50.421 秒 / 14,990.8 MiB；分开读取方案 11.796 秒 / 1,070.5 MiB。两条视频帧数、音视频时长、规格完全一致。完整核心复验首帧开启 13.517 秒 / 1,109.3 MiB，关闭 12.462 秒 / 1,057.0 MiB，没有硬件降级。这是本机这组长素材结果，不保证其他素材同幅度加速。

生产接入后补测用户同一 F 盘输出位置，加入 40% Hook BGM、原音量 100%，两路输出约 48–50 秒长片：首帧 insert 开启批次 15.442 秒 / 1,110.0 MiB，关闭批次 13.946 秒 / 1,059.1 MiB，均使用 NVIDIA、无降级/提交警告，直接生成正常命名的 MP4。验收临时结果已清理；旧任务的三条完成视频已恢复到原定正式文件名，大小保持一致。

最终后端回归 132 项及 74 个子测试通过，覆盖三轨 BGM、字幕、水印、分组/原时长、随机输出、去重 B 混合及首帧组合；测试断言原声独立读取与 seek 一致。Mac 尚未实机验证。

非整帧片段边界会受 24fps 量化影响：该长片首帧插入复验其中一条输出帧数未增加，但音频后移约一帧、音画尾差 7ms；不据此声称所有非整帧边界都严格多一个编码帧。

## 回归覆盖

### Windows 桌面保活管道与封面超时

2026-10-04 用户任务 `8bf9d728-1cc1-42d2-9e19-e7591a1682b1`：30 条基础成片全部完成，24 条封面成功，6 条封面取帧超时。该任务没有 WinError / 占用报错；6 条约 40 秒的耗时包含 30 秒取帧等待，不是主编码再次降速。

复现必须匹配桌面启动条件：Electron 给后端一个保持打开的 stdin 管道，`app.main.watch_parent` 线程阻塞读取它。抽帧继承此管道，FFmpeg 的交互输入检查与该同步读取冲突，PNG 已生成但进程无法退出。单独命令行取帧没有保活读取线程，会正常结束，因而不能只用终端验证。

在隔离目录对上述 6 条原始抽帧命令进行两路复测，stderr 使用文件避免测试自身管道阻塞：加入阻塞保活读取后，旧命令全部触及测试的 6 秒超时上限，6 张 PNG 均已完整写出；仅增加 `-nostdin` 后 6/6 正常结束，耗时 0.750–1.328 秒，文件大小与旧路径一致。测试不写入用户产出目录、不修改源素材。

生产修正只涉及输入隔离：抽帧加 `-nostdin`，`run_process` 子进程显式使用 `stdin=DEVNULL`，不继承软件的保活管道。没有缩短原有超时、隐藏警告、增加整片编码或改变抽帧滤镜。新增回归模拟保持打开且有读取线程的桌面管道，并检查抽帧仍只读取一个输入、输出一帧；同时回测桌面退出保活机制。

该修正后完整本地后端与 Agent 适配器回归 **134 项及 74 个子测试通过**；发布前前端 **21 项 runtime 测试与 Vite 构建通过**。

`tests/test_fused_cover.py` 覆盖整数/分数帧率、插入/替换帧数和音频、静音分组原时长、随机输出参数、取帧及编码回退、去重 B 画面回退、关闭零额外抽帧、随机选择独立、成功后被占用/停止仍保留、同名并发、独占预留冲突不覆盖、失败只清理自有文件。

测试已加入 Windows / macOS 构建工作流。CI 成功与 Mac 真机验证须以实际运行结果为准。
